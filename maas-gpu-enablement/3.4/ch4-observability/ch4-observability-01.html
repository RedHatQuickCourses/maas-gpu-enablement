4.1: Application Integration & The Rate Limit Reality

The platform is secure, and Finance is happy. Now, it is time to build apps.

Because OpenShift AI’s MaaS gateway is fully OpenAI-compatible, integrating ChocoTech’s existing applications requires almost zero code refactoring. However, because we built strict Token Rate Limits into our Subscriptions in Module 2, developers must know how to handle API rejections.

The "429 Too Many Requests" Trap

Imagine a Marketing developer writes a Python script to analyze 1,000 product reviews. Because the Marketing team is on the Bronze Plan, they are strictly limited to a specific amount of tokens per minute for the Qwen model.

Halfway through the script, the developer hits the limit. Kuadrant’s Limitador service intercepts the request and instantly returns an HTTP 429 Too Many Requests error. If the script is poorly written, the application crashes entirely.

Exercise 1: The Robust Python Load Generator

To survive in a governed MaaS ecosystem, developers must implement exponential backoff retry logic. When Kuadrant rejects a request, it provides a Retry-After HTTP header telling the application exactly how many seconds to wait before the token bucket resets.

Instead of running a local script, we are going to deploy a containerized Kubernetes Job that acts as a "chaos generator". It will intentionally spam the MaaS Gateway to trigger a rate limit, and use exponential backoff to handle it gracefully.

1. Secure the API Key
First, save the Bronze (Marketing) API key you generated earlier into a Kubernetes Secret.

export MAAS_API_KEY="<your-copied-bronze-api-key>"

oc create secret generic marketing-api-key \
  --from-literal=key=$MAAS_API_KEY \
  -n chocotech-models

2. Create the Python Script (ConfigMap)
We will store the Python script in a ConfigMap.

Notice the Routing URL: In OpenShift AI 3.4, the Data Plane inference endpoint is dynamically generated using the namespace and the model name. Our route is /chocotech-models/qwen3-8b/v1/chat/completions.

cat << 'EOF' | oc apply -f -
apiVersion: v1
kind: ConfigMap
metadata:
  name: marketing-batch-script
  namespace: chocotech-models
data:
  marketing-batch-job.py: |
    import os
    import time
    import requests
    import urllib3

    urllib3.disable_warnings(urllib3.exceptions.InsecureRequestWarning)

    api_key = os.getenv("MAAS_API_KEY")
    base_url = os.getenv("MAAS_URL")

    # OpenShift AI 3.4 Data Plane inference route
    url = f"{base_url}/chocotech-models/qwen3-8b/v1/chat/completions"

    headers = {
        "Authorization": f"Bearer {api_key}",
        "Content-Type": "application/json"
    }

    data = {
        "model": "qwen3-8b",
        "messages": [{"role": "user", "content": "Write a detailed 500 word essay on the history of chocolate manufacturing."}],
        "max_tokens": 600
    }

    print(f"Starting batch job against {url}...\n")

    for i in range(1, 20):
        print(f"Request {i}...", end=" ")
        response = requests.post(url, headers=headers, json=data, verify=False)

        if response.status_code == 200:
            print("✅ Success! Consumed tokens.")
        elif response.status_code == 429:
            # Kuadrant provides the exact wait time!
            retry_after = int(response.headers.get("Retry-After", 10))
            print(f"🛑 429 Rate Limit Hit! Sleeping for {retry_after} seconds...")
            time.sleep(retry_after)
        else:
            print(f"❌ Error: {response.status_code} - {response.text}")
            time.sleep(2)
EOF

3. Deploy the Batch Job
Deploy the Job to mount the script and execute it against the external Gateway Route.

export ROUTE_HOST=$(oc get route openshift-ai-inference -n openshift-ingress -o jsonpath='{.spec.host}')

cat <<EOF | oc apply -f -
apiVersion: batch/v1
kind: Job
metadata:
  name: marketing-chaos-job
  namespace: chocotech-models
spec:
  backoffLimit: 0
  template:
    spec:
      containers:
      - name: chaos-generator
        image: registry.access.redhat.com/ubi9/python-311
        command: ["/bin/bash", "-c"]
        args:
          - |
            pip install --quiet requests urllib3
            echo "Executing batch script against \$MAAS_URL..."
            python /opt/scripts/marketing-batch-job.py
        env:
        - name: MAAS_API_KEY
          valueFrom:
            secretKeyRef:
              name: marketing-api-key
              key: key
        - name: MAAS_URL
          value: "https://${ROUTE_HOST}"
        volumeMounts:
        - name: script-volume
          mountPath: /opt/scripts
      volumes:
      - name: script-volume
        configMap:
          name: marketing-batch-script
      restartPolicy: Never
EOF

Exercise 2: Watch the Throttling in Real-Time

Tail the logs of the container to watch the Python script hit Kuadrant’s rate limits:

oc logs -f job/marketing-chaos-job -n chocotech-models

You will see several ✅ Success messages as the Marketing team consumes their Bronze Tier quota. Eventually, Limitador will intervene, triggering the 🛑 429 Rate Limit Hit. Because of our robust error handling, the script will simply sleep and resume, ensuring ChocoTech’s applications never crash under load.

Exercise 3: Tuning Subscriptions (Finding the Sweet Spot)

In a real-world scenario, you may need to adjust a team’s token quota up or down based on their workload. If your script finished all 20 requests without hitting a 429 rate limit, it means the Marketing team’s token limit is too generous!

To force the rate limiter to trigger, you can dynamically patch the MaaSSubscription to severely restrict their limit (e.g., dropping it to 1,000 tokens per minute), and then redeploy the job to test the new boundaries.

1. Patch the Subscription Limit
Drop the token limit for qwen3-8b to 1000 tokens per minute:

oc patch maassubscription bronze-plan -n models-as-a-service --type=json -p='[
  {"op": "replace", "path": "/spec/modelRefs/1/tokenRateLimits/0/limit", "value": 1000}
]'

2. Delete the Completed Job
Because Kubernetes Jobs are immutable, you must delete the old deployment before re-running it:

oc delete job marketing-chaos-job -n chocotech-models

3. Redeploy and Watch
Scroll back up to Exercise 1, re-copy the Job deployment block (cat <<EOF | oc apply -f -), and paste it into your terminal to deploy the batch job again. Tail the logs, and you will see Limitador aggressively block the traffic much earlier in the cycle!

Feel free to keep experimenting! You can delete the job, tweak the token limits up or down, and redeploy to see exactly how Kuadrant mathematically protects your cluster’s GPU capacity in real-time.
