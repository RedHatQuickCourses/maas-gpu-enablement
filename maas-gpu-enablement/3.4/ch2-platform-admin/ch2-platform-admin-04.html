2.3: Defining Subscriptions and Token Limits

Exercise 1: Deploy the Subscriptions

We will use GitOps (Infrastructure-as-Code) to define the business logic for these three plans.

The "Pre-Wire" Trap: Notice the modelRefs section in the YAML below. Even though we will not deploy the llama-3-8b model until Module 3, MaaS allows us to "pre-wire" our governance.

Because the referenced model does not exist yet (missing the MaaSModelRef object), the OpenShift AI operator will immediately flag these subscriptions with a Failed phase status. This is expected! We are explicitly telling the platform: "When a model reference named llama-3-8b appears in the chocotech-models namespace, apply these limits."

Execute the following block to deploy all three MaaSSubscription policies into the centralized models-as-a-service namespace:

cat <<EOF | oc apply -f -
---
apiVersion: maas.opendatahub.io/v1alpha1
kind: MaaSSubscription
metadata:
  name: gold-plan
  namespace: models-as-a-service
spec:
  priority: 80
  owner:
    groups:
      - name: chocotech-quality-control
    users: []
  modelRefs:
    - name: llama-3-8b
      namespace: chocotech-models
      tokenRateLimits:
        - limit: 50000
          window: 1m
---
apiVersion: maas.opendatahub.io/v1alpha1
kind: MaaSSubscription
metadata:
  name: silver-plan
  namespace: models-as-a-service
spec:
  priority: 50
  owner:
    groups:
      - name: chocotech-rd
    users: []
  modelRefs:
    - name: llama-3-8b
      namespace: chocotech-models
      tokenRateLimits:
        - limit: 10000
          window: 1m
---
apiVersion: maas.opendatahub.io/v1alpha1
kind: MaaSSubscription
metadata:
  name: bronze-plan
  namespace: models-as-a-service
spec:
  priority: 10
  owner:
    groups:
      - name: chocotech-marketing
    users: []
  modelRefs:
    - name: llama-3-8b
      namespace: chocotech-models
      tokenRateLimits:
        - limit: 2000
          window: 1m
EOF

Expected output: The terminal will confirm the creation of gold-plan, silver-plan, and bronze-plan.

Verification & Diagnosing the Failure

Verify that the MaaS operator successfully registered the subscriptions, and observe the expected failure state:

oc get maassubscription -n models-as-a-service

Expected output:

NAME          PHASE    PRIORITY   AGE
bronze-plan   Failed   10         8s
gold-plan     Failed   80         8s
silver-plan   Failed   50         8s

If a subscription shows a Failed phase status in production, your first troubleshooting step as a Platform Engineer is to check the conditions for the exact failure reason:

oc describe maassubscription gold-plan -n models-as-a-service

You will see an error indicating that the model reference cannot be found. This will automatically resolve in Module 3 once we deploy the model!

You have successfully defined what the groups are allowed to do. However, a subscription alone does not open the door. In the next section, we will deploy the MaaSAuthPolicy to physically authorize this traffic at the network edge.
