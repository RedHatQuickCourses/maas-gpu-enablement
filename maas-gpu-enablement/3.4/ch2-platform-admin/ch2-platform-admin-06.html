2.5: Native API Key Management and programmatic access

With the organizational subscriptions defined, we must enable programmatic access for ChocoTech’s applications. The Quality Control team’s needs access to a Llama model to summarize test results.

OpenShift AI 3.4 introduces Native API Key Management, users can create, list, and revoke their own API keys for model access. Administrators can also provision and manage API keys on behalf of users. API keys can be permanent or configured with custom expiration times, and individual keys can be revoked without affecting other keys for the same user.

How API Keys Work in OpenShift AI 3.4

Before generating keys, it is crucial to understand how the MaaS controller handles identity and security at the network edge:

  • Show-Once Security: API keys are cryptographically secure strings starting with sk-oai-. The plaintext key is only displayed once during creation and cannot be retrieved later.

  • Immutable Subscription Binding: Every API key is strictly bound to a single subscription at the time it is minted. If a user belongs to multiple groups and creates a key without specifying a subscription, the system uses the subscription with the highest priority level.

  • The Group Snapshotting Vulnerability: API keys retain a snapshot of user group memberships from when the key was created. If a user is removed from a group, their existing API keys continue to grant access until you revoke them.

Self-Service vs. Programmatic Access

The platform supports two distinct workflows for generating keys:

  1. Creating API Keys by Users (Self-Service): The platform empowers developers to manage their own access. For keys, users navigate to Gen AI studio → API keys.

  2. Creating API Keys as Service Accounts (Programmatic Access): For automated applications, platform administrators centrally provision API keys on behalf of users or applications.

Enforce Global Security Guardrails

By default, users can create "Permanent" keys. To enforce security policies, you can set a maximum expiration period for API keys across the entire platform.

Execute the following command to patch the centralized Tenant custom resource and enforce a strict 90-day maximum lifetime (maxExpirationDays) for all new API keys:

oc patch tenant default-tenant -n models-as-a-service \
  --type merge \
  -p '{"spec":{"apiKeys":{"maxExpirationDays":90}}}'

Expected behavior: Anyone attempting to create an API key with an expiration longer than 90 days will now receive an error.

⚠️ The Group Membership "Gotcha" (Shadow IT Simulation)

Imagine a scenario where a ChocoTech R&D engineer transfers to a different department, so IT removes them from the chocotech-rd OpenShift group.

Because API keys snapshot group membership at creation time, the engineer’s old API key will still work and consume R&D’s Silver Plan quota until the key reaches its 90-day expiration!

To immediately revoke access after a group change, administrators must manually revoke the API keys for that user. You must utilize the Revoke user API keys administrative action in the dashboard (Gen AI studio → API keys) to immediately cut off access when an employee leaves or changes departments.

ChocoTech’s programmatic authentication is now secure and strictly governed. In Module 3, we will finally deploy the models and watch the MaaS catalog populate automatically!
