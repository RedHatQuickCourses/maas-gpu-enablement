MaaS Gateway Architecture and Troubleshooting

This section is under development

For platform engineers, the most complex aspect of deploying Models-as-a-Service (MaaS) is establishing the Gateway API routing. When developers report that their inference scripts are failing, or the dashboard Playground is spinning endlessly, the issue almost always lies in the network routing.

This appendix provides a deep dive into how traffic physically flows through the OpenShift AI architecture and provides the exact troubleshooting steps required to resolve the most common networking failures.

Part 1: The MaaS Traffic Flow Architecture

To successfully troubleshoot MaaS, you must understand the journey of an API request. When a developer executes a curl command against a model endpoint, the request traverses multiple layers of Kubernetes infrastructure.

  1. The OpenShift Router (openshift-ingress): The request first hits the cluster’s external edge. The OpenShift Router intercepts the HTTPS request based on the .spec.host defined in the openshift-ai-inference Route.

  2. The Gateway API (maas-default-gateway): The router forwards the traffic to the Gateway API. This is not a legacy OpenShift Route; it is the modern Kubernetes Gateway API (gateway.networking.k8s.io).

  3. The Policy Enforcement Point (Kuadrant): Before the Gateway allows the traffic to proceed, it pauses the request and consults Kuadrant.

    • Authentication (Authorino): Validates the sk-oai- Bearer token and confirms the user’s OpenShift group membership.

    • Rate Limiting (Limitador): Checks the Redis cache to ensure the user has not exceeded their MaaSSubscription token limits.

  4. The Inference Engine (KServe): If Kuadrant approves the request, the Gateway forwards the payload to the LLMInferenceService pod running vLLM or llm-d, which finally executes the matrix multiplication on the GPU and returns the response.

If any link in this chain breaks, the user receives an error.

Part 2: Common Gateway Failures and Resolutions

Based on real-world deployments, here are the three most common MaaS Gateway failures and exactly how to fix them.

Issue 1: The "503 Service Unavailable" Dead End

Symptom: Developers execute a curl command against what they believe is the Gateway URL (e.g., https://maas.apps.example.com), but they receive a massive block of HTML from OpenShift stating "Application is not available: The host doesn’t exist."

The Root Cause: Platform engineers often manually guess or hardcode the Gateway URL. However, if the openshift-ai-inference Route in the openshift-ingress namespace was created without a hardcoded host: parameter, the OpenShift Router auto-generates a unique hostname (e.g., openshift-ai-inference-openshift-ingress.apps…​). The router physically does not know what maas.apps…​ is.

The Fix: You must dynamically query OpenShift for the exact Auto-Generated Route Host, and instruct developers to use that specific URL.

# Retrieve the ACTUAL Gateway Route host
export ROUTE_HOST=$(oc get route openshift-ai-inference -n openshift-ingress -o jsonpath='{.spec.host}')

# Use this dynamic host for all API calls
curl -k https://${ROUTE_HOST}/maas-api/v1/models \
  -H "Authorization: Bearer $MAAS_API_KEY"

Issue 2: Dashboard Proxy "Error Loading Components"

Symptom: You deploy the MaaS infrastructure, but when you navigate to Gen AI Studio → API Keys in the dashboard, the UI crashes with a red "Error loading components" banner.

The Root Cause: The OpenShift AI dashboard uses a Backend-For-Frontend (BFF) proxy. Even if the external OpenShift Router is working perfectly, the dashboard pod itself does not inherently know where the Gateway API is located on the internal network. It loops back on itself and crashes.

The Fix: You must explicitly inject the MAAS_API_URL environment variable directly into the dashboard deployment.

# Capture the external Route URL
export ROUTE_HOST=$(oc get route openshift-ai-inference -n openshift-ingress -o jsonpath='{.spec.host}')

# Inject the URL into the Dashboard proxy
oc set env deployment/rhods-dashboard -n redhat-ods-applications MAAS_API_URL=https://${ROUTE_HOST}/maas-api

# Force a restart of the dashboard pods
oc rollout status deployment/rhods-dashboard -n redhat-ods-applications

Issue 3: Missing Gateway Annotations (TLS and Authorization Failures)

Symptom: The Gateway is deployed, but traffic fails to route to Authorino, or the ODH Model Controller keeps fighting your MaaS configurations. You might see TLS handshake failures or authorization policies that refuse to enforce.

The Root Cause: The Gateway resource must include two very specific annotations for the MaaS controller to function correctly. Without these, the gateway either fails to secure traffic or gets overwritten by competing controllers.

The Fix: You must verify and apply the required annotations to your maas-default-gateway in the openshift-ingress namespace.

  1. security.opendatahub.io/authorino-tls-bootstrap: "true": The MaaS controller detects this annotation and automatically creates an EnvoyFilter resource that configures the Envoy proxy to use TLS when communicating with Authorino. Without it, secure internal routing fails.

  2. opendatahub.io/managed: "false": This allows the MaaS controller to manage authorization policies without interference from the ODH Model Controller.

Run the following command to forcefully overwrite and apply these annotations to your Gateway:

oc annotate gateway maas-default-gateway -n openshift-ingress \
  security.opendatahub.io/authorino-tls-bootstrap="true" \
  opendatahub.io/managed="false" \
  --overwrite

By understanding the traffic flow and keeping these three troubleshooting strategies nearby, you can resolve the vast majority of network routing issues encountered in Models-as-a-Service deployments.
