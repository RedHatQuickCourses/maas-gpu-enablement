1.3: Enabling MaaS on your OpenShift AI platform

You have explored the business problem and understand the three-layer architecture. Now it is time to activate MaaS on ChocoTech’s OpenShift cluster. ChocoTech’s GPU infrastructure is already operational from prior AI/ML experiments. Rather than starting from scratch, you will transform this fragmented hardware into a centralized MaaS platform by enabling the components that provide governance, routing, and multi-tenant model serving.

This module guides you through the exact activation sequence: verifying required operators, creating the infrastructure foundation, deploying the required database, and patching the OpenShift AI platform to expose the MaaS features.

Step 1: Configuration check & operator verification

Before applying any configurations, ensure your cluster meets the baseline requirements. You must be running OpenShift version 4.20.0 (officially 4.19.9) or later. Furthermore, specific operators and monitoring stacks must be installed. If any of these are missing, the deployment will silently fail.

Ensure the following operators and settings are active:

  • User Workload Monitoring: This is absolutely critical for MaaS. Without it, the MaaS Tenant resource will show a Degraded status, and the platform will fail to collect token consumption metrics.

  • Red Hat OpenShift Service Mesh 3: Provides the underlying Istio networking that powers the Gateway API implementation.

  • Red Hat Connectivity Link (v1.2+): Delivers the Kuadrant governance framework.

  • Red Hat OpenShift AI (v3.4+): The core platform operator that manages the DataScienceCluster.

  • Leader Worker Set (LWS) Operator: Mandatory for llm-d orchestration to manage models that exceed single-node VRAM capacity.

  • Cluster Observability Operator: While MaaS core routing works without it, ChocoTech’s Finance team needs this to view the MaaS observability dashboard (Tech Preview) for token consumption tracking and showback reporting.


Need a quick sanity check, click & run this: 
oc get csv | grep -E "(servicemesh|rhcl|rhods|limitador|authorino|leader|cluster)"

If any operators are missing, install them from the OpenShift console (Ecosystem → Software Catalog) and wait for their status to reach Succeeded before continuing.

Step 2: The infrastructure foundation

The OpenShift AI operator acts as a strict gatekeeper. It will not provision the MaaS API unless the foundational network routing, security engines, and databases are actively running on the cluster.

Initialize the Governance Engine (Kuadrant)

The Connectivity Link operator manages Kuadrant (Authorino & Limitador), but Kuadrant itself must be explicitly initialized. A Kuadrant custom resource (CR) must be created and ready in the kuadrant-system namespace.

  • Authorino: Validates tokens and enforces zero-trust authentication.

  • Limitador: Tracks token consumption and enforces subscription-based token limits.

Create the namespace and Kuadrant instance:

cat <<EOF | oc apply -f -
apiVersion: v1
kind: Namespace
metadata:
  name: kuadrant-system
---
apiVersion: kuadrant.io/v1beta1
kind: Kuadrant
metadata:
  name: kuadrant
  namespace: kuadrant-system
spec: {}
EOF

Step 3: The Trap (Deploying without User Workload Monitoring)

Before we configure our Gateway and Database, let’s look at the most common failure point when deploying MaaS.

In OpenShift AI 3.4, User Workload Monitoring is strictly required. This is the underlying mechanism that tracks token consumption and rate limiting across the platform. If it is disabled, the core MaaS installation will fail to function properly and will display a Degraded status.

Let’s simulate this common misconfiguration. We will skip enabling User Workload Monitoring for now, proceed with the installation, and watch how the platform reacts.

Expand for instructions to enable user Workload monitoring

User Workload Monitoring is an OpenShift cluster setting that enables the Models as a Service (MaaS) platform to collect and expose usage data

  • It is required for the following reasons:

    • Tracking Consumption: It is the underlying mechanism that tracks token consumption, request counts, and rate limiting across the platform.

    • Without it, the platform cannot collect the token metrics necessary for enforcing subscription quotas or providing Finance teams with accurate chargeback data.

    • Platform Health: If User Workload Monitoring is not enabled, the core MaaS installation and the centralized Tenant custom resource will fail to function properly and will display a Degraded status.

cat <<EOF | oc apply -f -
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    enableUserWorkload: true
EOF

Verify User Workload Monitoring pods are running:

oc get pods -n openshift-user-workload-monitoring

If this fails to return results, try again after a 10-15 seconds.

Expected output (pods Running):

NAME                                   READY   STATUS    AGE
prometheus-operator-6bd7f9ddfc-vn49s   2/2     Running    0
prometheus-user-workload-0             6/6     Running    0
thanos-ruler-user-workload-0           4/4     Running    0

Step 4: Create the MaaS Gateway

Next, we establish the Front Door. According to Red Hat prerequisites, a Gateway named maas-default-gateway must exist in the openshift-ingress namespace. This becomes the single API endpoint for all of ChocoTech’s model inference traffic.

To ensure proper TLS hostname matching and external routing in a production environment, we will deploy the Gateway as an internal ClusterIP service and expose it using a native OpenShift Route with reencrypt TLS termination.

1. Create the infrastructure configuration

Create a ConfigMap to instruct the OpenShift service-ca-operator to auto-provision an internal TLS certificate (maas-gw-service-tls) and deploy the Gateway as a ClusterIP rather than an external load balancer.

cat <<EOF | oc apply -f -
apiVersion: v1
kind: ConfigMap
metadata:
  name: gw-options
  namespace: openshift-ingress
data:
  service: |
    metadata:
      annotations:
        # OpenShift service-ca-operator auto-provisions a TLS certificate into this Secret.
        service.beta.openshift.io/serving-cert-secret-name: "maas-gw-service-tls"
    spec:
      # ClusterIP avoids provisioning an external LoadBalancer; the OpenShift Route handles external ingress instead.
      type: ClusterIP
EOF

3. Deploy the Gateway

First, dynamically grab the OpenShift Gateway Controller class

export GW_CLASS=$(oc get gatewayclass -o custom-columns=NAME:.metadata.name,CTRL:.spec.controllerName --no-headers | grep "openshift.io/gateway-controller" | awk '{print $1}' | head -n 1)

Create the Gateway resource. Red Hat requires this resource to include two specific annotations for MaaS to function correctly. Notice that we omit explicit hostnames from the listeners to prevent SNI mismatches when the OpenShift Route passes traffic through.

cat <<EOF | oc apply -f -
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: maas-default-gateway
  namespace: openshift-ingress
  annotations:
    security.opendatahub.io/authorino-tls-bootstrap: "true"
    opendatahub.io/managed: "false"
  labels:
    app.kubernetes.io/name: maas-gateway
    istio.io/rev: openshift-gateway
    kuadrant.io/gateway: "true"
spec:
  gatewayClassName: ${GW_CLASS}
  infrastructure:
    parametersRef:
      group: ""
      kind: ConfigMap
      name: gw-options
  listeners:
  - name: http
    port: 80
    protocol: HTTP
    allowedRoutes:
      namespaces:
        from: All
  - name: https
    port: 443
    protocol: HTTPS
    tls:
      mode: Terminate
      certificateRefs:
      - group: ""
        kind: Secret
        name: maas-gw-service-tls
    allowedRoutes:
      namespaces:
        from: All
EOF
1 Authorino TLS Bootstrap: Enables TLS communication between the Gateway and Authorino.
2 Managed Status: Allows the MaaS controller to manage authorization policies without interference from the ODH Model Controller.

4. Expose the Gateway via OpenShift Route

Finally, create the OpenShift Route to act as the public entry point. This handles the external ingress and securely re-encrypts traffic back to the internal Gateway service.

cat <<EOF | oc apply -f -
apiVersion: route.openshift.io/v1
kind: Route
metadata:
  name: openshift-ai-inference
  namespace: openshift-ingress
  annotations:
    router.openshift.io/service-ca-certificate: "true"
spec:
  port:
    targetPort: 443
  tls:
    insecureEdgeTerminationPolicy: Redirect
    termination: reencrypt
  to:
    kind: Service
    name: maas-default-gateway-${GW_CLASS}
    weight: 100
EOF

Understanding the Gateway API architecture in OpenShift AI

Red Hat OpenShift AI dictates the requirements of the Gateway API (specific namespace locations, Gateway names, and annotations) but leaves the physical proxy implementation up to the cluster administrator, noting that configuration templates are community-maintained.

The benefit of this architecture is the separation of infrastructure from application logic. As a platform engineer, you only build the Gateway. When ChocoTech deploys a model and checks the "Publish as MaaS" box, they do not need to write any networking rules. The MaaS controller automatically generates the HTTPRoute behind the scenes. That route dynamically attaches itself to the maas-default-gateway, securely linking the public endpoint through the Kuadrant governance layer directly to the internal model pod.

Optional: Verify GatewayClass Controller Compliance

While the exact infrastructure deployment of the Gateway is flexible, the official Red Hat documentation explicitly requires that the GatewayClass backing your MaaS deployment is configured to use the OpenShift Gateway Controller (openshift.io/gateway-controller).

Run this quick sanity check to verify that your openshift-ai-inference GatewayClass was built using the correct underlying controller.

oc get gatewayclass ${GW_CLASS} -o jsonpath='{.spec.controllerName}{"\n"}'

Expected output:

openshift.io/gateway-controller

If the output matches, your underlying Gateway API infrastructure is fully compliant with Red Hat’s MaaS prerequisites.

Step 5: Configure Authorino Environment

The OpenShift service-ca-operator automatically handles the population of the cluster CA bundle. However, you are responsible for annotating the Gateway to trigger the automatic creation of the required EnvoyFilter for TLS. To get Models-as-a-Service (MaaS) running, you must configure the Authorino environment and verify the Gateway annotations.

First, you must configure the Authorino deployment with SSL environment variables so it can communicate securely with the MaaS API.

# Wait for the Authorino service to be created by the operator
echo "Waiting for Authorino service to initialize..."
until oc get service authorino-authorino-authorization -n kuadrant-system >/dev/null 2>&1; do
  sleep 5
done
echo "Authorino service is ready."

# Set SSL environment variables for outbound communication
oc -n kuadrant-system set env deployment/authorino \
SSL_CERT_FILE=/etc/ssl/certs/openshift-service-ca/service-ca-bundle.crt \
REQUESTS_CA_BUNDLE=/etc/ssl/certs/openshift-service-ca/service-ca-bundle.crt

# Generate the TLS certificate for Authorino
oc annotate service authorino-authorino-authorization -n kuadrant-system \
service.beta.openshift.io/serving-cert-secret-name=authorino-server-cert --overwrite

# Patch the Authorino resource to enable the TLS listener
oc patch authorino authorino -n kuadrant-system --type=merge --patch '
{
  "spec": {
    "listener": {
      "tls": {
        "enabled": true,
        "certSecretRef": {
          "name": "authorino-server-cert"
        }
      }
    }
  }
}'

Verify Authorino SSL Variables:

oc get deployment/authorino -n kuadrant-system -o jsonpath='{.spec.template.spec.containers[0].env[?(@.name=="SSL_CERT_FILE")].value}'

Expected output:

/etc/ssl/certs/openshift-service-ca/service-ca-bundle.crt

Verify Gateway Annotation:

oc get gateway maas-default-gateway -n openshift-ingress -o jsonpath='{.metadata.annotations.security\.opendatahub\.io/authorino-tls-bootstrap}'

Expected output: true

Note on Certificates: You must ensure your cluster already has a functional ingress controller with valid TLS certificates for external access before starting this procedure. If you are missing the maas-db-config secret or User Workload Monitoring, the Tenant resource will likely remain in a False or Degraded state.

Step 6: Deploy the MaaS API Database

In OpenShift AI 3.4, the platform features native API key management. To store these keys securely, you must have a PostgreSQL database and create a Secret named maas-db-config in the redhat-ods-applications namespace.

Deploy a lightweight PostgreSQL instance and the required secret for the MaaS API:

cat <<EOF | oc apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: maas-postgres
  namespace: redhat-ods-applications
spec:
  replicas: 1
  selector:
    matchLabels:
      app: maas-postgres
  template:
    metadata:
      labels:
        app: maas-postgres
    spec:
      containers:
      - name: postgres
        image: registry.redhat.io/rhel9/postgresql-15:latest
        env:
        - name: POSTGRESQL_USER
          value: "maasuser"
        - name: POSTGRESQL_PASSWORD
          value: "maaspass"
        - name: POSTGRESQL_DATABASE
          value: "maasdb"
        ports:
        - containerPort: 5432
---
apiVersion: v1
kind: Service
metadata:
  name: maas-postgres
  namespace: redhat-ods-applications
spec:
  selector:
    app: maas-postgres
  ports:
  - port: 5432
    targetPort: 5432
---
apiVersion: v1
kind: Secret
metadata:
  name: maas-db-config
  namespace: redhat-ods-applications
type: Opaque
stringData:
  DB_CONNECTION_URL: 'postgresql://maasuser:maaspass@maas-postgres:5432/maasdb?sslmode=disable'
EOF

Step 7: Platform activation & The "Degraded" Reality

With the operators verified, Kuadrant running, the Gateway established, and the database online, you can now instruct the OpenShift AI operator to build the MaaS API layer.

Enable the MaaS Backend and Llama Stack

Apply the patch to enable MaaS and the Llama Stack Operator in the DataScienceCluster:

oc patch datasciencecluster default-dsc --type=merge -p '{
  "spec": {
    "components": {
      "llamastackoperator": {
        "managementState": "Managed"
      },
      "kserve": {
        "modelsAsService": {
          "managementState": "Managed"
        }
      }
    }
  }
}'

Diagnose the Failure

Now, check the status of the Tenant custom resource. Because we intentionally skipped enabling User Workload Monitoring, the OpenShift AI Operator will refuse to report the MaaS component as healthy.

oc get tenants.maas.opendatahub.io default-tenant -n models-as-a-service -o jsonpath='{.status.conditions[?(@.type=="Ready")].status}'

Expected Output: False

To see exactly why it failed, read the condition message:

oc get tenants.maas.opendatahub.io default-tenant -n models-as-a-service -o jsonpath='{.status.conditions[?(@.type=="Ready")].message}'

The output will clearly indicate that User Workload Monitoring is missing. As a Platform Engineer, you will see this False or Degraded status frequently if prerequisites are missed.

The Fix: Enable User Workload Monitoring

Now that we have seen the failure, let’s fix the cluster. Apply the following ConfigMap to enable User Workload Monitoring:

cat <<EOF | oc apply -f -
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    enableUserWorkload: true
EOF

Wait a few moments, and check the Tenant status again:

oc get tenants.maas.opendatahub.io default-tenant -n models-as-a-service -o jsonpath='{.status.conditions[?(@.type=="Ready")].status}'

Expected Output: True

The Tenant resource is now healthy.

Enable the Dashboard (Gen AI Studio)

Even when deploying models via GitOps, administrators require the dashboard UI to manage user access tokens and monitor model usage. You must enable Gen AI Studio by patching the OdhDashboardConfig custom resource.

Apply the dashboard configuration patch:

oc patch odhdashboardconfig odh-dashboard-config -n redhat-ods-applications --type=merge -p '{
  "spec": {
    "dashboardConfig": {
      "modelAsService": true,
      "genAiStudio": true,
      "maasAuthPolicies": true
    }
  }
}'

What is the script below doing?

When you patch the OdhDashboardConfig, the OpenShift AI operator automatically spins up the Gen AI Studio components. However, you must explicitly tell the dashboard how to route traffic to the MaaS API. Without this script, the dashboard’s internal proxy gets confused, loops back on itself, and crashes with an "Error loading components" message when you try to access the API Keys menu.

Here is exactly what this script accomplishes:

  • Prevents Race Conditions (oc wait): Patching the dashboard config triggers the OpenShift AI operator to reconcile the deployment. This command pauses the script until the operator finishes its work, ensuring our custom variables aren’t overwritten mid-deployment.

  • Captures the Dynamic Route (export ROUTE_HOST): Because we configured our Gateway Route to auto-generate a host based on the cluster’s domain, we must dynamically query OpenShift to find out what that public URL actually is.

  • Injects the Routing Logic (oc set env): This is the critical fix. It injects the MAAS_API_URL environment variable directly into the dashboard deployment. This explicitly forces the dashboard’s Backend-For-Frontend (BFF) proxy to send all API Key and Model queries through our secure openshift-ai-inference Gateway, where Authorino can validate them.

  • Applies the Changes (oc rollout status): Forces the deployment to spin up new pods with the injected URL and waits for them to become healthy before releasing the terminal.

# Wait for the dashboard deployment to be fully available after patching the config
oc wait --for=condition=Available deployment/rhods-dashboard -n redhat-ods-applications --timeout=300s

# Capture the external Route URL
export ROUTE_HOST=$(oc get route openshift-ai-inference -n openshift-ingress -o jsonpath='{.spec.host}')

# Inject the URL into the Dashboard
oc set env deployment/rhods-dashboard -n redhat-ods-applications MAAS_API_URL=https://${ROUTE_HOST}/maas-api

# Wait for the Dashboard to restart with the new variable
oc rollout status deployment/rhods-dashboard -n redhat-ods-applications

Refresh your OpenShift AI browser window. The Gen AI Studio - API Key generation tab menu option will now appear in your left-hand navigation pane.

Step 8: Verification Summary

Before moving on to building ChocoTech’s subscription plans in Module 2, run this comprehensive verification script to confirm all components deployed successfully.

Manual File Creation Required: You must create this file manually before adding the content (for example, by using touch filename or opening a new file directly in your text editor).

Copy/Paste Tip: Due to web terminal buffer limitations, pasting the entire block of text at once may result in nothing being pasted.

  1. Copy and paste tasks 1 through 5 first.

  2. Once those are successfully pasted, copy and paste the remaining text.

 
cat > verify-maas-prereqs.sh <<'EOF'
#!/bin/bash

echo "=== MaaS Prerequisites Verification ==="
echo ""

# 1. OpenShift Version
echo "1. OpenShift Platform Version:"
OCP_VERSION=$(oc version -o json 2>/dev/null | jq -r '.openshiftVersion' 2>/dev/null || echo "ERROR")
echo "   Version: ${OCP_VERSION}"
[[ "${OCP_VERSION}" == "ERROR" ]] && echo "   ❌ FAILED" || echo "   ✅ PASSED"
echo ""

# 2. OpenShift AI Operator
echo "2. Red Hat OpenShift AI Operator:"
RHOAI_CSV=$(oc get csv -n redhat-ods-applications 2>/dev/null | grep rhods-operator | awk '{print $1}')
echo "   CSV: ${RHOAI_CSV:-NOT FOUND}"
[[ -z "${RHOAI_CSV}" ]] && echo "   ❌ FAILED" || echo "   ✅ PASSED"
echo ""

# 3. Red Hat Connectivity Link
echo "3. Red Hat Connectivity Link Operator:"
RCL_CSV=$(oc get csv -n openshift-operators 2>/dev/null | grep connectivity-link | awk '{print $1}')
echo "   CSV: ${RCL_CSV:-NOT FOUND}"
KUADRANT_STATUS=$(oc get kuadrant kuadrant -n kuadrant-system -o jsonpath='{.status.conditions[?(@.type=="Ready")].status}' 2>/dev/null || echo "ERROR")
echo "   Kuadrant Ready: ${KUADRANT_STATUS}"
[[ "${KUADRANT_STATUS}" == "True" ]] && echo "   ✅ PASSED" || echo "   ❌ FAILED"
echo ""

# 4. Llama Stack Operator
echo "4. Llama Stack Operator:"
LLAMA_STATE=$(oc get datasciencecluster default-dsc -o jsonpath='{.spec.components.llamastackoperator.managementState}' 2>/dev/null || echo "ERROR")
echo "   Management State: ${LLAMA_STATE}"
[[ "${LLAMA_STATE}" == "Managed" ]] && echo "   ✅ PASSED" || echo "   ⚠️  WARNING: Required for dashboard features"
echo ""

# 5. User Workload Monitoring
echo "5. User Workload Monitoring:"
UWM_ENABLED=$(oc get configmap cluster-monitoring-config -n openshift-monitoring -o jsonpath='{.data.config\.yaml}' 2>/dev/null | grep -o "enableUserWorkload: true" || echo "NOT ENABLED")
echo "   Status: ${UWM_ENABLED}"
[[ "${UWM_ENABLED}" == "enableUserWorkload: true" ]] && echo "   ✅ PASSED" || echo "   ❌ FAILED"
echo ""

# 6. PostgreSQL Database Secret
echo "6. PostgreSQL Database Secret:"
DB_SECRET=$(oc get secret maas-db-config -n redhat-ods-applications -o jsonpath='{.metadata.name}' 2>/dev/null || echo "NOT FOUND")
echo "   Secret: ${DB_SECRET}"
[[ "${DB_SECRET}" == "maas-db-config" ]] && echo "   ✅ PASSED" || echo "   ❌ FAILED"
echo ""

# 7. Gateway API
echo "7. Gateway API Resources:"
GW_STATUS=$(oc get gateway maas-default-gateway -n openshift-ingress -o jsonpath='{.status.conditions[?(@.type=="Programmed")].status}' 2>/dev/null || echo "NOT FOUND")
echo "   Gateway Programmed: ${GW_STATUS}"
[[ "${GW_STATUS}" == "True" ]] && echo "   ✅ PASSED" || echo "   ❌ FAILED"
echo ""

# 8. KServe Component
echo "8. KServe Component (Required for MaaS):"
KSERVE_STATE=$(oc get datasciencecluster default-dsc -o jsonpath='{.spec.components.kserve.managementState}' 2>/dev/null || echo "ERROR")
echo "   Management State: ${KSERVE_STATE}"
[[ "${KSERVE_STATE}" == "Managed" ]] && echo "   ✅ PASSED" || echo "   ❌ FAILED"
echo ""

echo "=== Summary ==="
echo "Review any ❌ FAILED items above before proceeding with MaaS deployment."
echo ""
EOF

chmod +x verify-maas-prereqs.sh
./verify-maas-prereqs.sh

If the output shows ✅ PASSED for the required components, ChocoTech’s underlying infrastructure is officially primed for centralized governance. Proceed to the Summary and troubleshooting page to close out this module.
