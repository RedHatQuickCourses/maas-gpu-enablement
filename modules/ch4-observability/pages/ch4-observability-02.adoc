= 4.2: Enabling Telemetry and Observability

The Marketing team's batch script successfully ran, consumed its token quota, and gracefully handled the `429 Too Many Requests` errors. The infrastructure is protected. 

However, when you log into the OpenShift AI dashboard to pull the billing report for the Finance team, the data might be missing. 

By default, to save space in the Prometheus database, OpenShift AI does not scrape high-cardinality rate-limiting or model-specific usage metrics. To satisfy Finance's chargeback requirements, you must explicitly enable telemetry across the Kuadrant governance layer and the Models-as-a-Service (MaaS) Tenant.


== Exercise 1: Enable Kuadrant Observability

Kuadrant uses a component called Limitador to physically enforce the token limits defined in your subscriptions. 

By enabling observability on the Kuadrant custom resource, you instruct the platform to create a `PodMonitor`. This tells Prometheus to start scraping Limitador for the exact rate-limiting metrics (like those 429 errors the Marketing team just generated) required for the MaaS observability dashboard.

Execute this command to patch the Kuadrant resource:

[source,role="execute"]
----
oc patch kuadrant kuadrant -n kuadrant-system \
  --type merge \
  -p '{"spec":{"observability":{"enable":true}}}'
----

*Expected Output:* `kuadrant.kuadrant.io/kuadrant patched`

To verify the `PodMonitor` was successfully created by the operator, run:

[source,role="execute"]
----
oc get podmonitor kuadrant-limitador-monitor -n kuadrant-system
----

== Exercise 2: Enable Tenant Telemetry

While Kuadrant tracks the rate limits, the MaaS Gateway tracks the actual inference tokens. You must enable telemetry on the `Tenant` custom resource to collect usage metrics—including token consumption, request counts, and model-specific usage patterns.

[IMPORTANT]
====
**Metric Cardinality & Privacy** +
In the patch below, `captureUser` and `captureGroup` are set to `false`. This is the enterprise default. Enabling user-level tracking on a cluster with thousands of developers will exponentially increase metric cardinality and can severely bloat the Prometheus database. We will rely on Subscription-level aggregation for our financial chargebacks.
====

Execute this command to patch your default MaaS Tenant:

[source,role="execute"]
----
oc patch tenants.maas.opendatahub.io default-tenant -n models-as-a-service \
  --type merge \
  -p '{
    "spec": {
      "telemetry": {
        "enabled": true,
        "metrics": {
          "captureOrganization": true,
          "captureUser": false,
          "captureGroup": false,
          "captureModelUsage": true
        }
      }
    }
  }'
----


*Expected Output:* `tenant.maas.opendatahub.io/default-tenant patched`

== Exercise 3: Verify the Prometheus Metrics Pipeline

Before we look at the UI dashboard, let's verify that Prometheus is successfully scraping the underlying data. We will query the Prometheus API directly to check for `authorized_calls` (the total API requests made to the models).

Run this command to query the Prometheus service inside the cluster:

[source,role="execute"]
----
oc exec -n openshift-monitoring sts/prometheus-k8s -c prometheus -- \
  curl -s 'http://localhost:9090/api/v1/query?query=authorized_calls' | jq
----

*Expected Output:*
You should see a JSON response containing metric data labeled with `limitador_namespace`, proving that Prometheus successfully captured the requests.

*(Note: If you query for `limited_calls` or `authorized_calls`, be aware that the `model` label does not appear on these metrics due to Kuadrant wasm-shim limitations; the `model` label only appears on `authorized_hits` )*

---

The telemetry pipeline is officially flowing. Every token consumed and every rate limit enforced is now being permanently recorded.

=== Deploy the Job again to generate metrics now that we are scraping the usage metric data.

[source,role="execute"]
----
export ROUTE_HOST=$(oc get route openshift-ai-inference -n openshift-ingress -o jsonpath='{.spec.host}')

cat <<EOF | oc apply -f -
apiVersion: batch/v1
kind: Job
metadata:
  name: marketing-chaos-job
  namespace: chocotech-models
spec:
  backoffLimit: 0
  template:
    spec:
      containers:
      - name: chaos-generator
        image: registry.access.redhat.com/ubi9/python-311
        command: ["/bin/bash", "-c"]
        args:
          - |
            pip install --quiet requests urllib3
            echo "Executing batch script against \$MAAS_URL..."
            python /opt/scripts/marketing-batch-job.py
        env:
        - name: MAAS_API_KEY
          valueFrom:
            secretKeyRef:
              name: marketing-api-key
              key: key
        - name: MAAS_URL
          value: "https://${ROUTE_HOST}"
        volumeMounts:
        - name: script-volume
          mountPath: /opt/scripts
      volumes:
      - name: script-volume
        configMap:
          name: marketing-batch-script
      restartPolicy: Never
EOF
----
