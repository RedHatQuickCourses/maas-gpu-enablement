== Learning objectives

By the end of this module, you will be able to:

* Explain the architectural difference between a governed `LLMInferenceService` deployment and an ungoverned legacy deployment.
* Provision model serving runtimes using `llm-d` (for distributed inference) or `vLLM`.
* Understand how the "Publish as MaaS" function automatically generates `MaaSModelRef` custom resources to register models with the gateway.
* Execute the critical post-deployment governance steps to link newly deployed models to existing `MaaSSubscription` and `MaaSAuthPolicy` resources.
* Understand the two-tier authentication architecture required for routing requests to External Models (Technology Preview).

== The deployment strategy

Deploying a model and making it accessible through MaaS is a strict, multi-step process. In this module, you will execute the following strategy to ensure complete governance:

[cols="1a,2a",options="header",frame="all",grid="rows"]
|===
| Phase | Action

| **1. Hardware & Runtime Sizing**
| Analyze the hardware requirements for your target models and select the appropriate serving runtime (`llm-d` or `vLLM`). 

| **2. The Deployment**
| Provision the model using the `LLMInferenceService` architecture. You will explicitly avoid the legacy deployment method to ensure the model does not bypass the MaaS gateway.

| **3. Registration (`MaaSModelRef`)**
| Use the "Publish as MaaS" feature to automatically generate a `MaaSModelRef` custom resource, notifying the MaaS platform that the model is ready for governance.

| **4. Post-Deployment Governance**
| A model published to MaaS is not immediately accessible. You will manually update your existing ChocoTech Subscriptions and AuthPolicies to append the newly generated model reference, officially closing the governance loop.
|===

By the end of this module, ChocoTech's business units will finally have self-service, heavily governed access to state-of-the-art AI models.
