ChocoTech's Quality Control team has been successfully using the `llama-3-8b` model for several weeks. Now, they want to upgrade to a new version that has been fine-tuned specifically on ChocoTech manufacturing defects.

"We cannot risk downtime," explains the QC Director. "Our production line depends on real-time defect detection. How do we update the model without causing an outage?"

This is a classic "Day 2" production challenge. Because you deployed the model using Models-as-a-Service (MaaS) and GitOps, updating it is safe, auditable, and completely seamless for the end users. Furthermore, Day-2 operations in MaaS go beyond just updating model weights—they encompass security lifecycles and cost monitoring.

== 1. Version Management Strategy

Production AI systems require disciplined version management, just like application code. ChocoTech uses semantic versioning for its model weights stored in the OCI registry or local vault:

* **v1.3.0:** Base Llama-3 8B Instruct (Currently deployed)
* **v1.4.0:** Fine-tuned on chocolate defect images (The requested upgrade)
* **v2.0.0:** Major architecture change (e.g., swapping to Llama-3 70B)

By keeping the model weights in distinct versioned paths, you ensure that the previous version is always preserved and ready for an instant rollback.

== 2. The MaaS Architectural Advantage

In a legacy, ungoverned AI environment, changing a model often meant changing the endpoint URL, issuing new credentials, and forcing developers to update their application code.

**OpenShift AI 3.4 eliminates this friction.** The Models-as-a-Service platform acts as a governance layer between users and the underlying model serving infrastructure.  Because the architecture separates the engine (`LLMInferenceService`) from the registration (`MaaSModelRef`), updating a model's weights is completely decoupled from its access control.

When you update the model weights, the Gold Plan token limits remain perfectly intact, the API keys generated by the developers remain valid, and the Gateway URL does not change.

== 3. The GitOps Update Workflow

To update the model, a Platform Engineer does *not* delete the running pod. Instead, they update the declarative YAML file in their Git repository. When updating the `LLMInferenceService`, the only line that needs to change is the `uri` pointing to the new vault location:

[source,yaml]
----
apiVersion: serving.kserve.io/v1alpha1
kind: LLMInferenceService
metadata:
  name: llama-3-8b
  namespace: chocotech-models
# ... [truncating for brevity] ...
spec:
  model:
    uri: oci://quay.io/redhat-ai-services/modelcar-catalog:llama-3-8b-v1.4.0  # <--- Update the path
----

=== Graceful Rollouts and the GPU Requirement
When you commit this change and apply it to the cluster, OpenShift AI and KServe perform a **Rolling Update**. 

[IMPORTANT]
====
**Hardware Prerequisite for Zero-Downtime:** To execute a graceful rollout, your OpenShift cluster **must have an additional equivalent GPU available**. 
====

1. The system spins up a completely new inference pod and begins downloading the `v1.1.0` weights into the new GPU's VRAM.
2. During this time, the `v1.3.0` pod continues serving live traffic from the Gateway. No user requests are dropped.
3. Once the `v1.4.0` pod reports a `Ready` status, KServe automatically flips the network route.
4. All new traffic seamlessly flows to `v1.4.0`. The old `v1.3.0` pod is then gracefully terminated, freeing up its GPU.

=== The Rollback 
If the Quality Control team reports that the `v1.4.0` model is hallucinating or underperforming, the rollback process takes seconds. You simply revert the Git commit, and KServe repeats the rolling update process to restore the known-good state.

== 4. Day-2 Governance and Observability

As ChocoTech's AI usage matures, platform engineers must also manage the lifecycle of user access and platform costs.

* **API Key Lifecycle Management:** You should mandate that teams rotate API keys periodically and revoke compromised keys immediately. It is critical to remember that API keys capture a user's group memberships at the exact time of creation. If a user leaves the Quality Control team, their existing API keys will continue to work until they expire or are manually revoked by an administrator.
* **Cost Attribution (Showback):** As usage scales, Finance will want to know which departments are consuming the most GPU compute. You can use the MaaS observability dashboard to monitor subscription-level usage metrics—such as token consumption and rate-limit violations—and export this usage data in CSV format for cost attribution and showback reporting.
