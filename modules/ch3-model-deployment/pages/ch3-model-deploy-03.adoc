= 3.2: Deploying the governed model via GitOps

====
WARNING: This section is under development
====

With the hardware math verified and the `LLMInferenceService` architecture selected, it is time to deliver the AI capabilities to ChocoTech's R&D team. 

In a production environment, pulling massive 16GB model weights directly from the public internet every time a pod scales up is highly inefficient and poses a security risk. Instead, ChocoTech uses a "Vault" strategy: downloading the model once to a high-speed S3-compatible storage array inside the cluster, where all inference pods pull their weights locally.

To simplify the deployment for this lab exercise, we will bypass the S3 setup and deploy our model using the **Modelcar** packaged format. We will pull the model directly from a public Red Hat OCI repository (`oci://quay.io/redhat-ai-services/modelcar-catalog:llama-3.1-8b-instruct`). While pulling the model upon each restart is not optimal for production, the OCI format offers a clean, streamlined solution for this lab exercise.

== 1. Extract the Serving Runtime (The Engine)

OpenShift AI includes certified, cluster-wide runtime templates. However, platform engineers often extract these templates into local project namespaces. 

*Why do we do this?* Localizing the serving runtime gives you absolute control over the compute engine. It allows you to inject custom environment variables, lock specific version tags, and apply unique accelerator configurations for ChocoTech's models without inadvertently impacting workloads in other departments.

Execute the following command to extract the official vLLM template from the central OpenShift AI namespace and install it locally into your `chocotech-models` project:

[source,role="execute"]
----
oc process vllm-cuda-runtime-template -n redhat-ods-applications | \
oc apply -f - -n chocotech-models
----

*Expected Output:* `servingruntime.serving.kserve.io/vllm-cuda-runtime created`.

== 2. Deploy the LLMInferenceService and MaaSModelRef

Because ChocoTech uses GitOps, we will deploy the model using declarative YAML rather than clicking through the dashboard UI. 

In OpenShift AI 3.4, a governed deployment requires two distinct resources working together:

1. **`LLMInferenceService`:** This provisions the actual inference engine, requests the GPU, and loads the weights into VRAM.
2. **`MaaSModelRef`:** This is the critical registration resource. It is the programmatic equivalent of checking "Publish as MaaS" in the dashboard. It explicitly notifies the MaaS platform that the model exists so it can be exposed through the API Gateway.


Execute the following block to deploy both resources into the `chocotech-models` namespace:

[source,role="execute"]
----
cat <<EOF | oc apply -f -
apiVersion: serving.kserve.io/v1alpha1
kind: LLMInferenceService
metadata:
  name: llama-3-8b
  namespace: chocotech-models
spec:
  # THE VAULT: Pointing to our Modelcar OCI image
  model:
    uri: oci://quay.io/redhat-ai-services/modelcar-catalog:llama-3.1-8b-instruct
    
  # THE ENGINE: Utilizing the localized runtime we extracted in step 1
  servingRuntime: "vllm-cuda-runtime"
  
  # THE SCHEDULER: Bypassing standard round-robin for intelligent llm-d dispatching
  router:
    scheduler:
      template:
        containers:
          - name: main
            args:
              - '--pool-group'
              - 'inference.networking.x-k8s.io'
              - '--pool-name'
              - '{{ .ObjectMeta.Name }}-inference-pool'
            
  # ENGINE TUNING: Injecting native vLLM parameters for maximum throughput
  template:
    spec:
      containers:
        - name: main
          env:
            - name: VLLM_ADDITIONAL_ARGS
              value: "--max-model-len=8192 --gpu-memory-utilization=0.90"
              
  # THE HARDWARE: Requesting exact VRAM and GPU requirements
  placement:
    accelerator:
      name: "nvidia.com/gpu"
      count: 1
---
apiVersion: maas.opendatahub.io/v1alpha1
kind: MaaSModelRef
metadata:
  name: llama-3-8b
  namespace: chocotech-models
spec:
  modelRef:
    kind: LLMInferenceService
    name: llama-3-8b
EOF
----

Check the status condition to verify the model is healthy and ready to serve traffic. *(Note: This may take several minutes as the node pulls the 16GB OCI image).*

[source,role="execute"]
----
oc wait --for=condition=Ready llminferenceservice/llama-3-8b -n chocotech-models --timeout=600s
----

== 3. The Post-Deployment Governance Step

A critical architectural concept in OpenShift AI 3.4 is that publishing a model to MaaS (via the `MaaSModelRef`) does not immediately grant anyone access to it. 

If you had deployed this model in a vacuum, the model would sit completely isolated. After publishing, a cluster administrator must create a subscription and add this model to make it accessible to user groups.

However, we **pre-wired ChocoTech's governance strategy** in Module 2! You already explicitly listed the `llama-3-8b` model in your Gold, Silver, and Bronze subscriptions. 

Because the architecture operates dynamically, as soon as the `LLMInferenceService` reports `Ready`, the MaaS controllers instantly map the model to your existing subscriptions and begin enforcing your exact token limits at the Kuadrant Gateway.

== Alternative: The UI Deployment Walkthrough

While GitOps is the standard for Platform Engineers, administrators can also deploy models directly through the OpenShift AI dashboard UI. 

When deploying a generative AI model via the dashboard wizard, selecting **Publish as MaaS** under Model availability makes the model accessible to users through the MaaS gateway by automatically generating the `MaaSModelRef` object.

[WARNING]
====
**Explicit Warning: The "Legacy Deployment Method" Checkbox** +
Models deployed for MaaS use the `LLMInferenceService` architecture, which integrates with the MaaS gateway for subscription-based quota enforcement. If you deploy models via the UI, you must ensure the **Use legacy deployment method** checkbox is cleared. The legacy deployment method uses traditional KServe InferenceService resources with serving runtimes, bypassing MaaS architecture entirely.
